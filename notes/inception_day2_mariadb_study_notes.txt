3. LINUX USER mysql VS MARIADB USER wpuser
============================================================

[CORE] [EVAL]

There are TWO completely different kinds of "users".

A. Linux user:

    mysql

This is a Linux operating-system account.

It was automatically created when Debian installed:

    mariadb-server

I checked it with:

    id mysql

and saw something like:

    uid=100(mysql) gid=101(mysql)

Why does it exist?

MariaDB should not run as Linux root.

Instead:

    mariadbd --user=mysql

runs the database server with a restricted Linux account.


B. MariaDB database user:

    wpuser

This user exists INSIDE MariaDB.

WordPress will later use it to log into the database.

Example:

    CREATE USER 'wpuser'@'%'
    IDENTIFIED BY '...';

[MEMORY]

    Linux mysql user
        = runs the MariaDB PROCESS

    MariaDB wpuser
        = WordPress uses this account to ACCESS DATABASE DATA


============================================================
4. WHY NOT RUN MARIADB AS root?
============================================================

[CORE] [EVAL]

Linux root has very powerful permissions.

If MariaDB ran as root and MariaDB were compromised,
the process could potentially have much more power over the system.

Running MariaDB as:

    mysql

follows the principle of least privilege:

    Give a process only the permissions it actually needs.

Could MariaDB run as another user such as "yuan"?

Technically yes, if that Linux user existed and had all required permissions.

But Debian already creates a dedicated:

    mysql

user for MariaDB, so using it is the sensible/default choice.

5. /run/mysqld AND THE SOCKET CONFUSION
============================================================

[CORE] [DEBUG]

At first this felt completely random:

    mkdir -p /run/mysqld
    chown mysql:mysql /run/mysqld

I did not want to blindly create a random directory.

So instead I tried starting MariaDB first:

    mariadbd --user=mysql

MariaDB eventually produced:

    Can't start server : Bind on unix socket: No such file or directory

and referred to:

    /run/mysqld/mysqld.sock

This taught me WHY the directory is needed.

What is:

    /run/mysqld/mysqld.sock

?

It is a Unix socket file.

Very simplified:

    MariaDB client
         ↓
    mysqld.sock
         ↓
    MariaDB server

It is another form of program-to-program communication.

This is conceptually related to sockets I learned in IRC,
but here it is a Unix socket for local communication.

6. WHY mkdir -p /run/mysqld?
============================================================

[CORE]

MariaDB wanted to create:

    /run/mysqld/mysqld.sock

but:

    /run/mysqld

did not exist.

So:

    mkdir -p /run/mysqld

means:

    Create the directory MariaDB needs.

The command is no longer random because I personally saw the error first.


============================================================
7. WHY chown mysql:mysql /run/mysqld?
============================================================

[CORE]

After creating the directory, MariaDB gave:

    Permission denied

because:

    /run/mysqld
    owner = root

but MariaDB was running as:

    mysql

So Linux user mysql could not write the socket file there.

Command:

    chown mysql:mysql /run/mysqld

Breakdown:

    chown
        = change owner

    mysql:mysql
        = new owner : new group

    /run/mysqld
        = directory being changed

Meaning:

    Change /run/mysqld so that Linux user mysql
    and Linux group mysql own it.

[MEMORY]

    chown = change owner

9. PID 1
============================================================

[CORE] [EVAL]

Inside a Docker container:

    PID 1

is the main process.

I confirmed:

    PID 1 = mariadbd

Desired architecture:

    Container
    └── PID 1 = mariadbd

Why does this matter?

    mariadbd alive
        ↓
    container alive

    mariadbd dies
        ↓
    container stops

This means Docker accurately reflects whether the real service is alive.


============================================================
10. WHY NO & ?
============================================================

[EVAL] [CORE]

In a shell:

    &

means:

    Run this command in the background
    and immediately return control to the shell.

Example:

    mariadbd &

means MariaDB runs in the background.

Why is this bad for Inception if used as a keep-alive trick?

Bad example:

    mariadbd &
    tail -f /dev/null

Then:

    MariaDB could crash
        ↓
    tail -f keeps running
        ↓
    Docker still says container is alive

[EVAL]

The evaluation sheet explicitly checks that I do NOT use fake keep-alives,
background-process tricks, infinite loops, tail -f, sleep infinity, etc.

Correct:

    Container
    └── mariadbd
          ↑
      real foreground/main process

11. docker exec
============================================================

[CORE] [EVAL]

General pattern:

    docker exec -it <container> <command>

Meaning:

    Execute a command inside an already-running container.

Example:

    docker exec -it mariadb-test bash

means:

    Start Bash inside mariadb-test
    and attach my terminal to Bash.

Example:

    docker exec -it mariadb-test mariadb

means:

    Start the MariaDB CLIENT directly
    inside mariadb-test
    and attach my terminal to it.

Important:

    docker exec -it mariadb-test mariadb bash

does NOT mean:

    start MariaDB then Bash

It means:

    run command "mariadb"
    with argument "bash"

18. DOCKER VOLUME
============================================================

[CORE] [EVAL]

Without a volume:

    Container
    └── /var/lib/mysql
          ↓
       DB data

Delete container
    ↓
data can disappear

With a Docker named volume:

    Docker volume: mariadb-data
          ↓ mounted into
    Container: /var/lib/mysql

Create the storage:

    docker volume create mariadb-data

Mount the storage:

    -v mariadb-data:/var/lib/mysql

Breakdown:

    mariadb-data
        = named Docker volume

    /var/lib/mysql
        = location inside the container

[MEMORY]

    docker volume create
        = create storage

    -v volume:path
        = mount/connect storage into container

24. SHELL if SYNTAX
============================================================

[CORE]

My first-start check:

    if [ ! -d "/var/lib/mysql/mysql" ]; then
        echo "First MariaDB startup"
    fi

Breakdown:

    if
        = start condition

    [ ... ]
        = test something

    -d path
        = is this path a directory?

    !
        = NOT

    ;
        = finish the test command

    then
        = if condition is true, run next commands

    fi
        = end the if block

So:

    if [ ! -d "/var/lib/mysql/mysql" ]; then

means:

    If /var/lib/mysql/mysql does NOT exist as a directory,
    this is probably a fresh MariaDB startup.

26. THE STARTUP SCRIPT
============================================================

[CORE] [EVAL]

My startup script now has this overall job:

    container starts
        ↓
    prepare runtime directories
        ↓
    fix ownership
        ↓
    check first startup
        ↓
    if first startup:
        initialize MariaDB

Important lines:

    #!/bin/sh
        Run the script using sh.

    set -eu
        -e = stop if a command fails
        -u = error if using undefined variable

    mkdir -p /run/mysqld
        Create MariaDB runtime directory.

    chown -R mysql:mysql ...
        Give mysql ownership.
        -R = recursive.

    if [ ! -d "/var/lib/mysql/mysql" ]; then
        Detect first initialization.

    mariadb-install-db ...
        Initialize fresh MariaDB data.

    exec mariadbd --user=mysql
        Replace the shell script with the real MariaDB server.

28. CMD VS RUN VS ENTRYPOINT
============================================================

[CORE] [EVAL]

RUN:

    runs during docker build
        ↓
    prepares/changes the IMAGE

CMD:

    default command when docker run starts the container

ENTRYPOINT:

    defines the startup program for the container

My MariaDB flow:

    ENTRYPOINT ["/usr/local/bin/init.sh"]

then:

    init.sh
        ↓
    initialization logic
        ↓
    exec mariadbd

Once init.sh itself starts mariadbd,
I do not need a duplicate CMD that starts mariadbd again.

30. WHY CLEAN /var/lib/mysql DURING BUILD?
============================================================

[CORE]

During:

    apt-get install mariadb-server

the package may put initial MariaDB data into:

    /var/lib/mysql

But runtime DB data should be created when the container starts,
not baked into the image.

So:

    rm -rf /var/lib/mysql/*

after installation.

Mental model:

    IMAGE
        = contains MariaDB SOFTWARE

    VOLUME
        = contains MariaDB RUNTIME DATA
